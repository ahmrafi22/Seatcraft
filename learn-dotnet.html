Value types vs reference types

The classic interview question. Two ways a variable can hold data:

value type

Holds the data itself. Copying copies the data.

int, bool, double, char, DateTime, struct

int a = 5; int b = a; b = 9;
// a is still 5

reference type

Holds a pointer to the data. Copying copies the pointer.

string, class, record, arrays, List

var a = new List<int>();
var b = a; b.Add(1);
// a also has 1 now

Why your entities have private set

Look at this line again:

C#
public string Roll { get; private set; }

It means: anyone can read Roll, but only the class itself can change it.

Why? So nobody outside can do this:

C#
candidate.Roll = "";   // ❌ blocked. Roll can never be empty.

Instead you must go through a method that validates. That's what Create() is for — it's the only door in.

This is called encapsulation. If an interviewer asks "how do you protect invariants in your domain model?" — the answer is: private setters plus factory methods that validate. That's exactly what you built.

Records — the short version

You used record a lot for DTOs and solver inputs. A record is a class that gets value equality and immutability for free.

C#

Compare: two class objects with the same data are not equal. Two record objects with the same data are equal. That's why the solver tests can compare plans with Assert.Equal.

Architecture

Interfaces and Dependency Injection

This is the single most important concept in your codebase, and the most common interview topic at this level.

An interface is a contract

It says "whatever implements me must have these methods" — without saying how.

the contract
public interface IPlanCache{    Task<T?> GetAsync<T>(string key);    Task SetAsync<T>(string key, T value, TimeSpan ttl);    Task RemoveAsync(string key);}

Your project has two implementations of this exact interface:

InMemoryPlanCache

Uses RAM. For local development. No Redis needed.

DistributedPlanCache

Uses Redis. For production, shared across servers.

Nothing that uses IPlanCache knows or cares which one it gets. That's the point.

Dependency Injection in one picture

Instead of a class creating what it needs, it asks for it. Something else supplies it.

❌ without DI — tightly coupled
public class SeatPlanService{    // this class decides, and is stuck with that decision    private readonly DistributedPlanCache _cache = new DistributedPlanCache();}
✅ with DI — asks for a contract
public class SeatPlanService(ISeatCraftData data, IPlanCache cache){    // "give me anything that satisfies IPlanCache"    // it does not know or care whether that's Redis or RAM}

That syntax — parameters right after the class name — is a primary constructor. It's C# 12. It saves you writing a constructor and assignment by hand.

Where the wiring happens

One file registers everything: Infrastructure/DependencyInjection.cs

C#
// "when someone asks for IPlanCache, give them DistributedPlanCache"services.AddSingleton<IPlanCache, DistributedPlanCache>();// "when someone asks for ISeatCraftData, build a SeatCraftData"services.AddScoped<ISeatCraftData, SeatCraftData>();

Singleton vs Scoped vs Transient

Guaranteed interview question. It's about how long an object lives.

LifetimeCreatedUsed for
AddSingletonOnce, foreverCache, config, locks — stateless or shared
AddScopedOnce per HTTP requestDbContext, services — the default choice
AddTransientEvery time it's requestedLightweight, stateless helpers
The trap question: "Can you inject a Scoped service into a Singleton?"
No. The Singleton lives forever; the Scoped one dies after the request. The Singleton would hold a dead object. .NET actually throws an exception at startup if you try.
Concurrency

async and await — the part everyone fakes understanding

Your entire API is async. If you can explain this clearly, you're ahead of most candidates.

The problem it solves

When your API asks the database for 5,000 candidates, the server waits. If it blocks a thread while waiting, that thread can't serve anyone else. With 100 concurrent users, you run out of threads.

async/await lets the thread go do other work while waiting, then come back when the data arrives.

SeatCraft.Application/Exams/ExamService.cs — simplified
public async Task<ExamDto> GetAsync(Guid id){    var exam = await _data.Exams.FindAsync(id);    if (exam is null)        throw new NotFoundException($"Exam {id} was not found.");    return _mapper.ToDto(exam);}
👆 Click a line above.

The rules, stated plainly

  1. async Task<T> means "this returns a T, but asynchronously". The caller gets a promise, not the value.
  2. await means "pause here, give the thread back, resume when done".
  3. Never .Result or .Wait() — that blocks the thread and can deadlock. It's the #1 async mistake.
  4. Async all the way up. If a method calls an async method, it should be async too.
Why the method names end in "Async"? It's a convention, not a rule the compiler enforces. FindAsync, SaveChangesAsync, GetAsync. It tells the caller "you'll need to await this".

Why your allocation runs in the background

Solving 5,000 seats takes ~80ms. That's fine for an HTTP request. But the design you built doesn't rely on that — it uses a queue:

the flow
// 1. HTTP request returns IMMEDIATELY with a run idreturn Ok(new { id = run.Id, status = "Queued" });// 2. A BackgroundService picks it up on another thread// 3. Client polls GET /runs/{id} for progress

That's why the Postman collection had to poll instead of getting the answer in one call.

Querying

LINQ — SQL for objects

LINQ lets you filter and transform collections with readable method calls. You used it constantly.

C# — the same query, three ways
// plain loopvar result = new List<Candidate>();foreach (var c in candidates)    if (c.SubjectGroup == "Science") result.Add(c);// LINQvar result = candidates    .Where(c => c.SubjectGroup == "Science")    .OrderBy(c => c.Roll)    .Select(c => c.FullName)    .ToList();

c => c.Roll is a lambda — an inline function. Read it as "given c, return c.Roll".

The methods worth memorising

OrderBy / OrderByDescendingSort

Any(...)Does at least one match? Returns bool

The IQueryable vs IEnumerable question

This one separates juniors from mid-level. It's in your JD ("Good understanding of ... LINQ").

IEnumerable

Runs in memory. Pulls everything first, then filters.

Slow on big tables.

IQueryable

Builds a SQL query. Filters run in the database.

Only matching rows travel.

C#
// IQueryable: becomes "SELECT * FROM candidates WHERE Roll LIKE '%R1%'"IQueryable<Candidate> q = db.Candidates.Where(c => c.Roll.Contains("R1"));// IEnumerable: downloads ALL rows, then filters in memory 💀IEnumerable<Candidate> q = db.Candidates.ToList().Where(c => c.Roll.Contains("R1"));

The difference is the .ToList(). It forces the query to execute before the filter. Same code, wildly different performance.

This is also the N+1 query problem. If you loop over 100 exams and hit the database inside the loop, you make 101 queries. The fix is to load related data up front with Include() or project with Select().
Web

How a request becomes a response

ASP.NET Core is the web framework. Your API is built from three ideas: middleware, controllers, and DI.

1. The middleware pipeline

Every HTTP request passes through a chain of handlers, in order. Each one can act, pass it on, or stop it.

Program.cs — the actual order in your project
app.UseSerilogRequestLogging();          // 1. log itapp.UseMiddleware<ExceptionHandlingMiddleware>(); // 2. catch errorsapp.UseSwagger();                        // 3. dev docsapp.UseAuthentication();               // 4. who are you? (JWT)app.UseMiddleware<TenantResolutionMiddleware>(); // 5. which tenant?app.UseAuthorization();                // 6. are you allowed?app.UseRateLimiter();                  // 7. slow down abusersapp.MapControllers();                    // 8. finally, your code
Order matters, and it's a classic interview question. Authentication must come before authorization — you can't check permissions before you know who the user is. Exception handling goes early so it wraps everything.

C# is the language — the syntax you write. .NET is the platform that runs it. C# compiles to IL, and the CLR (part of .NET) executes that IL. .NET also supports F# and VB.NET, which compile to the same IL.
Value types (int, bool, struct) hold the data directly and live on the stack; copying copies the value. Reference types (class, string, arrays) hold a pointer to heap memory; copying copies the pointer, so both variables see the same object. That's why mutating a shared List affects both references.
It lets a thread be released while waiting on I/O. async marks a method as returning a Task; await suspends the method and returns the thread to the pool until the operation completes. This is why an API can handle many concurrent requests without one thread per request.
They block the calling thread synchronously. In a context with a synchronization context (classic ASP.NET, UI), that causes deadlocks — the thread waits for the task, and the task needs that same thread to finish. Always await instead.
Singleton: one instance for the app's lifetime. Scoped: one per HTTP request (DbContext lives here). Transient: a new one every time it's resolved. You cannot inject a Scoped service into a Singleton — the Singleton outlives the request and would hold a disposed object.

Looping over N entities and hitting the database once per item, producing N+1 queries instead of one. Fix it by loading related data up front with Include(), or by projecting everything you need in a single Select().
A class declares what it needs as constructor parameters instead of creating them itself. The container supplies them. Benefits: you can swap implementations (Redis cache vs in-memory) without touching the class, and you can inject fakes in tests.
